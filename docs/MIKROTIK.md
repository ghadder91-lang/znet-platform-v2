# ربط MikroTik — الإصدار 1.4 التجريبي

## ما يعمل

واجهة إعداد اتصال لكل شبكة، تشفير اسم المستخدم وكلمة المرور بمفتاح الخزنة، اختبار يدوي، قراءة معلومات الجهاز، استيراد HotSpot User Profiles، ربط الفئات بها وفصل الربط. لا توجد كتابة أو توليد مستخدمين أو استيراد كلمات مرور كروت من الراوتر. الربط لا يغير سعر الفئة أو حجمها أو صلاحيتها. لا يتضمن إنشاء VPN تلقائيًا.

يعتمد الموصل على RouterOS 7 REST API الرسمي عبر HTTPS وحساب قراءة مخصص. يستخدم طلبين GET ثابتين:

- `/rest/system/resource` مع اختيار خصائص الجهاز والإصدار والموارد.
- `/rest/ip/hotspot/user/profile` مع اختيار المعرف والاسم والسرعة ومهل الجلسة والخمول وعدد المستخدمين المشتركين.

مراجع الإعداد الرسمية التي روجعت:

- https://manual.mikrotik.com/docs/developer-guides/rest-api/
- https://help.mikrotik.com/docs/spaces/ROS/pages/56459266/HotSpot+-+Captive+portal

## تجهيز الراوتر بواسطة مسؤول الشبكة

1. تحقق من إصدار RouterOS 7 ووجود HotSpot Profiles المطلوب ربطها. RouterOS 6 وPPPoE وRADIUS ليست ضمن هذا الموصل.
2. جهّز وصول خادم زد نت إلى عنوان الراوتر عبر VPN أو شبكة موثوقة. لا يلزم فتح إدارة الراوتر لكل الإنترنت.
3. فعّل خدمة `www-ssl` بشهادة موثوقة تطابق عنوان الاتصال. راجع إجراءات الشهادات في المرجع الرسمي بما يناسب إصدارك.
4. أنشئ مستخدمًا مخصصًا ومجموعة بصلاحيات `read,api,rest-api`، وقيد مصدر اتصال المستخدم إلى خادم المنصة. لا تستخدم حساب admin أو تمنح write/sensitive لهذا الإصدار.
5. اختبر الوصول من الخادم. لا تعطل التحقق من TLS عند وجود خطأ شهادة؛ أصلح الشهادة أو أضف سلطة إصدارها إلى الثقة.

## إعداد الخادم

المسؤول وحده يحدد وجهة كل شبكة في `.env`. المعرف هو UUID الظاهر في صفحة الشبكة، وليس اسمها. مثال توضيحي يجب استبداله:

```dotenv
MIKROTIK_ENABLED=true
MIKROTIK_TARGETS_JSON='{"NETWORK_UUID":"https://router.example.com:443"}'
```

يجب أن يكون العنوان أصل HTTPS فقط، دون مسار `/rest` أو اسم مستخدم أو كلمة مرور أو معاملات. لا يوجد حقل في طلبات المتصفح لاختيار عنوان بديل. التفعيل مع جدول فارغ يبقي الشبكات دون وجهة. عند تغيير متغيرات البيئة أعد إنشاء حاوية التطبيق:

```sh
docker compose up -d --force-recreate app
```

لا تضع بيانات دخول الراوتر في هذا الجدول. يدخلها صاحب الشبكة في الخطوة الثانية بالواجهة. كل تعديل لبيانات الدخول يلغي Profiles وروابط الفئات السابقة ويستلزم فحصًا وربطًا جديدين. تغيير العنوان المعتمد يمنع استخدام بيانات محفوظة للعنوان القديم حتى يعاد حفظها.

إذا كانت الشهادة صادرة من CA خاصة، ضع شهادة CA العامة في `certs/router-ca.pem` على الخادم، ثم أنشئ `compose.override.yaml` محليًا:

```yaml
services:
  app:
    environment:
      NODE_EXTRA_CA_CERTS: /run/certs/router-ca.pem
    volumes:
      - ./certs/router-ca.pem:/run/certs/router-ca.pem:ro
```

أعد إنشاء الحاوية. لا تضع مفتاح الراوتر الخاص في المنصة، ولا تستخدم NODE_TLS_REJECT_UNAUTHORIZED=0؛ الموصل يفرض التحقق من TLS صراحة. إدارة DNS والعناوين المعتمدة وشبكة الخادم مسؤولية المشغّل؛ قيد حركة الخروج إلى الأجهزة المعتمدة عند النشر.

## الاستخدام

افتح الشبكة ← ربط MikroTik. اتبع تجهيز الوصول، ثم حفظ بيانات الدخول، ثم اختبار الاتصال وتحديث Profiles. اختر Profile لكل فئة واحفظ الربط. اختر «فصل Profile» لإلغاء ربط فئة، أو أكد فصل الاتصال لحذف بيانات دخوله والروابط محليًا دون تغيير الراوتر والكروت والمبيعات.

نجاح الفحص يعني استجابة الجهاز في وقت الفحص فقط؛ لا توجد مراقبة اتصال مستمرة هنا. تصبح النتيجة قديمة بعد 15 دقيقة، ويمنع ربط فئة جديدة حتى فحص ناجح حديث. الصورة المحفوظة للـProfiles تبقى عند فشل تحديث جديد وتظهر نتيجة الفشل. إذا تغير الاسم أو الخصائص المختارة أو اختفى Profile، يصبح ربطه غير صالح حتى المراجعة. تغييرات خصائص أخرى غير مختارة لا يكشفها هذا الإصدار؛ لا تستخدم الربط ضمانًا تلقائيًا لتوافق الباقة.

## حدود التنفيذ والتدقيق

- مهلة مطلقة 12 ثانية لكل طلب، وحد أقصى 512 KiB للاستجابة و500 Profile.
- لا يتبع تحويلات HTTP؛ أخطاء الراوتر الخام وبيانات الدخول لا تعاد إلى العميل ولا تسجل في سجل النشاط.
- فحص واحد للشبكة في الوقت نفسه، وفاصل دقيقة بين المحاولات لنفس إعداد الاتصال. تعديل الإعدادات ينشئ نسخة جديدة.
- لا تُحفظ نتيجة فحص جارٍ إذا تغيرت بيانات الاتصال أو فُصل الربط أثناء انتظاره.
- تحديثات الاتصال وربط الفئات تستخدم أرقام نسخ لمنع الكتابة فوق تعديل جلسة أخرى.
- آخر 100 نتيجة فحص محفوظة، والعشر الأخيرة ظاهرة. سجل النشاط منفصل.
- تعتمد البيانات المشفرة على VOUCHER_VAULT_KEY؛ احتفظ به مع خطة الاستعادة ولا تستبدله عشوائيًا.

## ما تم اختباره وما بقي

اجتازت النسخة 48 اختبارًا آليًا، بينها خادم HTTPS محلي بشهادة اختبار لرفض شهادة غير موثوقة، قبول CA محددة، رفض إعادة التوجيه، أخطاء الدخول، كبر الاستجابة، JSON غير صالح وانتهاء المهلة. اختبارات الموصل تحاكي بيانات RouterOS وحالات التزامن وتغير Profiles والعزل. نجح البناء واختبار واجهة HTTP للتطبيق.

لم يحدث اتصال براوتر MikroTik حقيقي، ولم يُنفذ اختبار توليد أو بيع عبره. قبل الاعتماد: اختبر إصدار الراوتر الفعلي، صلاحيات المستخدم، شهادة الوصول، فشل الشبكة، تغير Profile واستعادته، والفحص البصري على الهاتف. Docker والمتصفح لم يُختبرا في هذه البيئة. الربط التجاري بالمحافظ وSMS والتوليد الآلي ما زال غير مكتمل.

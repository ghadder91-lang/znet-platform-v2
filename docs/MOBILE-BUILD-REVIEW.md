## البنية
- app/: واجهات Next.js وواجهات API للمصادقة والمخزون والإدارة والحسابات والمطابقة والمختبر وMikroTik والتوقعات.
- server/: منطق المصادقة والتشفير والمعاملات وSQLite والتسليم والمطابقة والتحكم بالشبكات.
- drizzle/: ترحيلات SQL تطبق تلقائيًا عند فتح قاعدة البيانات.
- scripts/: الإدارة والنسخ والاستعادة واختبار HTTP وعاملا التسليم والتوقعات.
- tests/: تسعة ملفات اختبارات Node، بإجمالي 57 اختبارًا بعد إضافة ملف اختبارات طلبات الواجهة.
- Dockerfile: Node 24 وبناء Next standalone وتشغيل مستخدم node.
- compose.yaml: التطبيق وعاملا الخلفية وCaddy وvolumes دائمة.
- pnpm-lock.yaml وpackageManager: تثبيت pnpm 11.25.0؛ يتطلب Node >=24 بسبب node:sqlite.

## الأولويات
### P0 — قبل محاولة النشر
1. اختيار v2 الذي يحتوي المصدر. لا تستخدم v3 الفارغ ولا تنقل الملفات إليه تلقائيًا دون قرار.

3. تجهيز خادم Linux مع Docker Compose ونطاق DNS وHTTPS وvolumes دائمة. لا تكفي GitHub Pages لتطبيق Node/SQLite هذا. يجب اختيار الخادم الفعلي قبل إعداد نشر آلي.
4. إنشاء .env على الخادم بواسطة scripts/init.mjs؛ حفظ مفتاح التشفير خارج الخادم بشكل آمن، وعدم رفعه إلى GitHub. ملف .env.example مرجع فقط ومفتاحه فارغ عمدًا.
5. إصلاح إجراء الاستعادة ليوقف التطبيق والعاملين؛ العامل forecast-worker يفتح قاعدة البيانات ويبقى عاملًا عند إيقاف app وحده.

### P1 — قبل إطلاق تجاري
- اتفاق ووثائق واختبارات قبول من مزودي المحافظ والبنوك وSMS؛ ثم تنفيذ الموصلات الحقيقية، والتحقق من الإشعارات والتكرار والاستثناءات والتسويات. لا نفترض شكل API خارجي.
- تجربة Docker الفعلية مع HTTPS وحفظ البيانات بعد إعادة التشغيل، واختبار استعادة خارج الخادم ثم خطة تحديث وتراجع تراعي ترحيلات البيانات.
- اختبار شاشة هاتف فعلية، حمل وأمان ومراقبة أخطاء وتنبيهات ونسخ احتياطي مجدول.
- الإبقاء على نسخة تطبيق واحدة وSQLite محلية. لا يوجد في هذه المراجعة ما يثبت ملاءمة البنية لـ50 ألف شبكة أو تعدد replicas؛ يلزم قياس ومعمارية بيانات تتناسب مع نتائج الحمل.

### مكتمل — معالجة ESLint وبوابة الجودة
أصلحت تحميل البيانات الأولي في تسع لوحات باستخدام اشتراك طلب قابل للإلغاء؛ يتوقف تحديث الحالة عند مغادرة اللوحة، وتُهمل الاستجابات المتأخرة. أبقيت حواجز ترتيب طلبات المخزون والنشاط. عولجت روابط Next والتنقل بعد المصادقة مع تحديث بيانات الخادم، وأزيلت المتغيرات غير المستخدمة. لم تُعطل قواعد ESLint ولم تضف تأخيرات صورية.

أضيف أمر pnpm lint بحد تحذيرات صفر، وأصبح شرطًا في GitHub Actions. أضيفت أربعة اختبارات لوصول البيانات وأخطاء الخادم وإلغاء النقل والاستجابات المتأخرة أثناء تحليل JSON.

## اختبار تشغيل الحاويات والاستعادة
أضيف scripts/docker-smoke.mjs بعد بناء الصورة في GitHub Actions. يشغل حاوية بلا منافذ منشورة، بمفتاح وبيانات اختبار مؤقتة، ويفحص HTTP وملفات الواجهة والمصادقة والمخزون المشفر، ثم عاملي الخلفية، وإعادة إنشاء الحاوية على volume نفسه. بعد ذلك ينشئ نسخة احتياطية ويستعيدها في volume جديد ويتحقق من الحساب والكرت المفكوك تشفيره. ينظف موارده المؤقتة في النهاية ولا يلمس بيانات الإنتاج.

تشغيله يدويًا بعد بناء الصورة: `node scripts/docker-smoke.mjs IMAGE_TAG`. نتيجة التنفيذ الموثقة هي نتيجة خطوة Verify container runtime and recovery في طلب الدمج #1. هذا الاختبار لا يغطي Caddy أو HTTPS الخارجي أو حمل الإنتاج أو الربط مع مزود حقيقي.

### عيب كشفه اختبار الحاويات
نجح تشغيل التطبيق وملفات الواجهة والعاملين وحفظ المخزون بعد إعادة إنشاء الحاوية، لكن الاستعادة من volume للقراءة فقط أخفقت لأن SQLite احتاج ملفات WAL/SHM جانبية في مجلد المصدر. عُدّل restore.mjs ليأخذ نسخة مؤقتة خاصة، يتحقق من بصمتها والمفتاح وسلامة قاعدة البيانات، ثم ينسخها إلى وجهة جديدة دون استبدال ملفات موجودة. أضيف تحقق يمنع إنشاء ملفات جانبية في مصدر النسخة الاحتياطية.
